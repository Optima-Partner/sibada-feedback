## 0. 什么时候用这份手册 + 职责边界

### 0.1 适用场景

| 场景 | 说明 | 走哪节 |
|------|------|--------|
| **平台软件重装** | 同一 ECS 重装，或换一台新 ECS（同 VPC）重新部署平台。阿里云资源都在、ACR 镜像在、RDS/NAS 数据在。 | [§4](#4-平台重装-runbook命令--验证--回滚) |
| **数据层恢复** | RDS 数据库或 NAS 文件丢失/损坏，从备份恢复。 | [§5](#5-数据层恢复) |

> **不在本手册范围**：平台的日常部署 / 版本升级由 Optima 负责（见运维文档 🔴 章）。本手册是「Optima 不可用时本院能自助重建」的兜底 + 「当前环境到底怎么搭的」as-built 记录。

### 0.2 职责边界（重建时谁做什么）

| 层 | 内容 | 归属 |
|----|------|------|
| **云资源层** | ECS / RDS / NAS / ACR 的开通与配置、安全组、VPC、DNS 解析、域名 ICP 备案、**RDS/NAS 备份策略** | **本院阿里云运维** |
| **平台软件层** | 镜像拉取、compose 起服务、配 `.env.prod`、DB 建库/迁移、冒烟 | 本手册可执行（Optima 或本院技术人员照做） |
| **镜像构建** | 从源码 build 各服务镜像（`*:prod`） | **Optima**（需源码 + 构建链） |

> ⚠️ **本手册假设本院 ACR（`<ACR 命名空间>` 命名空间）里的 `*:prod` 镜像还在**。若 ACR 也被清空，镜像需从源码重建 → 联系 Optima。云资源层的备份（RDS 自动备份、NAS 快照）**归本院阿里云运维配置与保管**，和 RDS 一样属于基础设施职责。

## 1. 系统概览（as-built）

### 1.1 服务清单（17 服务：13 常驻 + 4 run-once）

编排文件：`docker/compose.prod.yml`（compose 项目名 `sibada-prod`）。镜像统一来自本院 ACR：
`<ACR-VPC-endpoint>/<ACR 命名空间>/<名>:prod`。

| 容器（container_name） | 职责 | 对外端口 | 类型 |
|------------------------|------|----------|------|
| `sibada-caddy` | HTTPS 反代 + 自动签证书（6 子域块 / 7 域名） | 80 / 443 | 常驻 |
| `sibada-logto` | 登录 / OIDC 授权服务 | 3001（OIDC 公网）/ 3002（admin，仅 127.0.0.1） | 常驻 |
| `sibada-logto-proxy` | nginx sidecar，给 gw-core 拉 OIDC discovery（保证 issuer 一致） | 内部 | 常驻 |
| `sibada-gw-core` | 对话网关；挂 docker.sock，**为每个会话 spawn 一个 bridge 容器** | 8080 | 常驻 |
| `sibada-agent`（`agent-runtime`） | AI 运行时 **base 镜像**（bridge 的模板，非 bridge 本身） | 内部 | 常驻 |
| `sibada-backend` | 业务后端（数字人 / 音视频 / 审核 / 区域） | 内部（Caddy 反代） | 常驻 |
| `sibada-web` | 前端 Next.js | 内部（Caddy 反代） | 常驻 |
| `sibada-admin`（`gw-admin`） | 网关后台 | 仅 127.0.0.1:3090 | 常驻 |
| `sibada-generation` | 图片 / 海报 / 语音 / 数字人生成（GrsAI/DashScope/HeyGen） | 内部 | 常驻 |
| `sibada-scout` | 抖音 / 小红书 / 视频号调研（TikHub） | 内部 | 常驻 |
| `sibada-optima-skills` | Skill marketplace registry | 内部 | 常驻 |
| `sibada-minio` | 对象存储（skills 用） | 内部 | 常驻 |
| `sibada-redis` | 任务队列缓存（不持久化） | 内部 | 常驻 |
| `sibada-logto-bootstrap` | Logto 库 seed | — | **run-once**（Exited 0） |
| `sibada-logto-pw` | 应用 Logto admin 密码 | — | **run-once** |
| `sibada-prod-minio-init-1`（compose 未设 container_name） | 建 minio bucket | — | **run-once** |
| `sibada-migrate` | 业务库迁移（sibada_dev） | — | **run-once**（seed 恒 exit 1，见坑） |

> **bridge 机制（重要）**：真正跑用户对话/技能的是 `gw-core` 动态起的 **per-session bridge 容器**（`optima-bridge-ses_*`），用的镜像是 `LOCAL_AGENT_IMAGE = <ACR 命名空间>/sibada-agent:prod`（**派生镜像**，含全部斯巴达技能 + CLI + `SKILL_PACK=default`）。而常驻的 `agent-runtime`（容器名 `sibada-agent`）是 gateway **base 镜像**（`SKILL_PACK=ecommerce`，无斯巴达技能）——**两者不是一回事**。要更新斯巴达 agent 能力，重建 / promote 的是 `sibada-agent:prod`，然后 `docker rm` 掉旧 bridge。

### 1.2 存储布局

| 位置 | 存什么 | 备份 |
|------|--------|------|
| **RDS**（6 库 3 用户） | 业务数据 + 登录数据 | ✅ 7 天自动备份（[§5](#5-数据层恢复)） |
| **NAS** `/mnt/nas/sibada` | `_shared/kb`（企业知识库 bare repo + 个人库）、`{userId}`（会话工作空间）、`_published`（成片视频） | ❌ **当前无备份**（[§5](#5-数据层恢复)） |
| **本地数据盘** `/mnt/data`（`/dev/vdb` 100G） | `docker`/`containerd`（镜像与层）、`minio`、`agent-workspace` | 无（可重建） |
| **docker named volumes** | `sibada_prod_caddy_data`（证书）、`sibada_prod_caddy_config`、`sibada_prod_agent_workspace` | 无（证书丢会自动重签） |

- **RDS 6 库 / 3 用户**：`optima_dev`（gw-core）、`optima_skills`、`optima_generation`、`optima_scout` → 属 `optima` 用户；`logto` → 属 `logto` 用户（需 CREATEROLE）；`sibada_dev`（schema=`sibada`）→ 属 `sibada_dev` 用户。
- ⚠️ **docker + containerd 的数据盘要放 `/mnt/data`**，别留在根盘（`/dev/vda3` 只有 40G）——历史上根盘满导致过「会话刷新变空」事故（见运维文档 §根盘满）。新装 ECS 时务必先配（[§4 阶段 A](#阶段-a--ecs-初始化)）。

### 1.3 网络与域名

- **主域名**：`ops.spider-net.com.cn`（裸域 = app 主入口）。
- **6 个子域块 / 7 个域名**（`Caddyfile.prod` 定义，各签独立证书，泛解析或 A 记录都指向 ECS 公网 IP）：
  - 裸域 / `app.` → 前端（双绑定）；`api.` → 业务后端；`gw.` → 网关；`auth.` → Logto **OIDC**（logto-proxy:3001）；`admin.` → 网关后台；`console.` → Logto **admin console**（logto:3002）。
  - 🔴 **`console.` 不能漏**：后端调 Logto Management API 走它（`LOGTO_ADMIN_ENDPOINT`），缺失 → `/api/admin/*` 全 503（stage 2026-07-02 踩过）。
- **端口**：公网只需 `80`/`443`（+ Logto OIDC `3001`、gw-core `8080`）；Logto admin `3002` 与 gw-admin `3090` 的**宿主端口**仅绑 `127.0.0.1`、走 **SSH 隧道**（首次 setup 用），不用开安全组。（稳态下 admin console 经 `console.` 子域 + Caddy 走 docker 网络到 `logto:3002`，不经宿主端口。）
- **HTTPS**：Caddy 自动 ACME（Let's Encrypt），HTTP-01 challenge 走 `:80`。**前提：域名已 ICP 备案**（cn `:443` 未备案会被阿里云 SNI 拦）。
- ⚠️ **换 base 域名**：`Caddyfile.prod` 的 6 个站点块**只写死子域前缀**（app/api/gw/auth/admin/console），域名后缀由 `BASE_DOMAIN` 参数化（`{$BASE_DOMAIN:...}`，compose 传入 caddy 容器）。换 base 域名只需改 `.env.prod` 的 `BASE_DOMAIN` + **重 build `sibada-web`**（`NEXT_PUBLIC_*` 是 build-time inline）+ 配 DNS，**不必手改 `Caddyfile.prod`**。

## 2. 前置：需要哪些阿里云资源（描述性）

> 这一节只**说明重建需要什么资源、什么规格**，不手把手教开通——开通与配置属本院阿里云运维职责。

| 资源 | 规格要求 | 实际参数从哪查 |
|------|----------|----------------|
| **ECS** | ≥4C8G、Ubuntu 22.04、数据盘 ≥100G（`/dev/vdb`）、公网 IP、与 RDS/NAS **同 VPC** | 阿里云控制台 → 云服务器 ECS |
| **RDS** | PostgreSQL **16**、同 VPC、白名单含 ECS 网段、有高权限账号、可空库起步 | 控制台 → RDS（内网地址 + 高权账号名） |
| **NAS** | NFS、同 VPC | 控制台 → NAS（文件系统 ID + 挂载点域名） |
| **ACR（企业版）** | 专用命名空间、**VPC endpoint 已 link 到 ECS 所在 VPC** | 控制台 → 容器镜像服务（实例 + VPC endpoint 域名） |
| **安全组** | 放行 `22`（SSH）/`80`/`443`；`3001`（OIDC）与 `8080`（网关）按需 | 控制台 → ECS 安全组 |
| **域名 + DNS** | 已 **ICP 备案**；**泛解析（推荐，自动覆盖 `console.`）** 或逐条 A 记录（须含 `console.`）→ ECS 公网 IP | 域名服务商 / 云解析 |

> 本手册为**脱敏公开版**，具体实例 ID、内网地址、账号名等以 `<占位符>` 表示 —— 这些值在**贵院自己的阿里云控制台**里可直接查到；平台侧配置（`.env.prod`、镜像仓库地址等）向 Optima 索取。

> ⚠️ **ACR VPC endpoint 必须 link 到 ECS 的 VPC**（控制台：ACR 实例 → 访问控制 → VPC → 添加），否则本院 ECS 推/拉镜像会 `no such host`。且该 endpoint 的私网 DNS 记录曾丢失过（[§7 坑](#7-当前基线--真实踩过的坑速查)）。

## 3. 凭据：.env.prod 要配哪些（无明文）

### 3.1 权威副本与离机备份

- **生产权威副本**：`/opt/sibada/docker/.env.prod`（就在 ECS 上，随平台运行）。
- **离机完整备份**：由 **Optima 在密码库中保管**一份完整副本（2026-07-25 起），重建时向 Optima 索取。
- 🔴 **`.env.prod` 是重建的命根子**。尤其 **`ENCRYPTION_KEY` 一旦丢失，RDS 里的加密数据（数字人/音色绑定、加密字段）永久无法解密** → 数据层恢复直接失败。**每次改动 `.env.prod` 后，务必同步更新离机备份。**

### 3.2 变量清单（4 类，共 ~42 项）

> 下表只列「有哪些 / 什么含义 / 值从哪来」，**不含明文值**。真实值在生产 `.env.prod`、Optima 保管的密码库、以及各第三方账户后台。

**A. 部署时生成（`openssl` 随机）—— 重装若要保留数据必须复用原值**

| 变量 | 生成方式 | 备注 |
|------|----------|------|
| `ENCRYPTION_KEY` | `openssl rand -hex 32` | 🔴 丢失=加密数据报废，必须复用原值 |
| `JWT_SECRET` / `INTERNAL_SERVICE_TOKEN` / `ADMIN_API_KEY` | `openssl rand -hex 32` | |
| `MINIO_ROOT_USER`(hex16) / `MINIO_ROOT_PASSWORD`(hex32) | `openssl rand` | |
| `OPTIMA_DB_PASSWORD` / `LOGTO_DB_PASSWORD` / `SIBADA_DEV_DB_PASSWORD` | `openssl rand -base64 24` | 3 个应用 DB 用户密码，须与 RDS 角色一致（`init-rds-prod.sh` 建/改） |
| `OAUTH_CLIENT_ID` / `OAUTH_CLIENT_SECRET` | 占位 `disabled-not-used` | sibada 不走 user-auth，dummy 即可 |

> 注：`POSTGRES_SUPERUSER_PASSWORD`、`SIGNED_URL_SECRET` 是 stage 遗留占位——prod compose **未接线**（无 postgres 容器；`SIGNED_URL_SECRET` 未透传给任何容器），保留不影响。**RDS 高权账号密码是 `RDS_SUPER_PASSWORD`**（账号名与密码见本院 RDS 控制台 / 向 Optima 索取），[§4 阶段 B](#阶段-b--rds-建库) 建库时用。

**B. 本院第三方账户密钥（值在各家后台，Optima 亦有备份）**

`SILICONFLOW_API_KEY`（AI 对话，**须国内站**）、`HEYGEN_API_KEY`（数字人）、`GRSAI_API_KEY`（图片）、`DASHSCOPE_API_KEY`（语音/OCR）、`TIKHUB_API_KEY`（调研）。空置可选：`BFL_API_KEY` `GROQ_API_KEY` `FASHN_API_KEY` `PIAPI_KEY`。

**C. Logto setup 产出（首次 setup 后从 Logto 控制台拷）**

`LOGTO_APP_ID` / `LOGTO_APP_SECRET`（gw-admin Traditional Web，机密客户端）、`LOGTO_M2M_APP_ID` / `LOGTO_M2M_APP_SECRET`（backend 调 Management API）、`SIBADA_WEB_LOGTO_APP_ID`（前端 SPA，也派生 backend 的 `SIBADA_LOGTO_CLIENT_ID` admin 闸口）、`LOGTO_ADMIN_PASSWORD`（Logto 控制台登录）。**重装（Logto 库在 RDS 未丢）时这些值不变，直接沿用原 `.env.prod`。**

**D. 普通配置（非密钥）**

`BASE_DOMAIN`、`PUBLIC_IP`、`RDS_HOST`、各 `*_URL` / `*_BASE_URL`、`DEFAULT_PROVIDER/MODEL/RUNTIME`、`GRSAI_REGION=cn`。

> ⚠️ **易错项**：`SILICONFLOW_BASE_URL` 必须 `https://api.siliconflow.cn/v1`（国内站 key 在 `.com` 报 401）；`HEYGEN_BASE_URL` 必须走 CloudFront 反代 `<HeyGen 反代地址（向 Optima 索取）>`（直连 `api.heygen.com` 被 GFW 阻断，表现为数字人训练返回空错误）。

## 4. 平台重装 runbook（命令 + 验证 + 回滚）

> **前提**：阿里云资源在（[§2](#2-前置需要哪些阿里云资源描述性)）+ 本院 ACR `*:prod` 镜像在 + 有 `.env.prod`（向 Optima 索取，[§3.1](#31-权威副本与离机备份)）。
> **原则**：逐阶段执行，每阶段验证通过再进下一步。给 ECS 的多行/带引号脚本一律**本地写好再 `scp` 过去跑**，别 inline heredoc over ssh。

代码同步到 ECS：把 `docker/`（`compose.prod.yml` / `Caddyfile.prod` / `logto-proxy.prod.conf` / `scripts/*`）放到 `<ECS>:/opt/sibada/docker`。ECS 从 GitHub 不通时，用 `git archive <ref> | ssh <ECS> 'tar -x -C /opt/sibada'` 传。

### 阶段 A — ECS 初始化

只在**新 ECS**或首次装时需要（幂等，重复跑无害）：

```bash
# 在本院 ECS 上（deployer，NOPASSWD sudo）
NAS_MOUNT_TARGET=<NAS 挂载点域名> \
DATA_DEVICE=/dev/vdb \
CUST_ACR_USER=<ACR 登录用户> CUST_ACR_PASSWORD=<ACR 登录密码> \
  sudo -E bash /opt/sibada/docker/scripts/bootstrap-ecs-prod.sh
```

做的事：格式化/挂数据盘 `/mnt/data`（写 fstab）→ 装 docker + compose（apt 走阿里云 mirror）→ 挂 NAS `/mnt/nas/sibada`（写 fstab）→ 建 `/mnt/data/{minio,agent-workspace}` + `/mnt/nas/sibada/{_shared/kb,_published}` → ACR login。

**A.1 docker/containerd 数据落 `/mnt/data`（防根盘满，务必先做）**：`bootstrap` 不改 docker data-root，需手动配（否则镜像/层堆在 40G 根盘）：
- `/etc/docker/daemon.json` 加 `"data-root": "/mnt/data/docker"`（保留 `registry-mirrors`）+ 日志 rotation `"log-driver":"json-file","log-opts":{"max-size":"50m","max-file":"3"}`。
- `/etc/containerd/config.toml`：`version = 3` + `root = "/mnt/data/containerd"`。
- 给 docker/containerd 各加 systemd drop-in `RequiresMountsFor=/mnt/data`（防重启时 daemon 抢在挂载前起、写进裸挂载点）。
- 顺序：先配置再首次拉镜像。若是已跑起来后迁移，迁移步骤为「停服务 → `rsync -aHAX` 搬数据 → 改配置 → 起服务」，建议联系 Optima 协助。

**验证**：`docker info | grep "Docker Root"` = `/mnt/data/docker`；`df -h /mnt/data /mnt/nas/sibada`；`docker login` 成功。
**坑**：ACR VPC endpoint 私网 DNS 若丢 → push/pull `no such host`。修：`/etc/hosts` 加 `<ACR endpoint 内网 IP> <ACR-VPC-endpoint>`（根治=控制台开「自动配置 DNS 解析」）。

### 阶段 B — RDS 建库

**仅全新空库**时跑（数据恢复场景**跳过**，库已随恢复回来，见 [§5](#5-数据层恢复)）：

```bash
RDS_HOST=<RDS 内网地址> \
RDS_SUPER_USER=<RDS 高权账号> RDS_SUPER_PASSWORD=<RDS 高权账号密码> \
OPTIMA_DB_PASSWORD=<.env.prod> LOGTO_DB_PASSWORD=<.env.prod> SIBADA_DEV_DB_PASSWORD=<.env.prod> \
  bash /opt/sibada/docker/scripts/init-rds-prod.sh
```

建 3 用户（`optima`/`logto`（CREATEROLE）/`sibada_dev`）+ 6 库。幂等（存在则改密码）。
**验证**：脚本末尾打印「6 库」清单齐全。

### 阶段 C — 起 Logto 层

```bash
cd /opt/sibada/docker
docker compose -f compose.prod.yml --env-file .env.prod up -d logto-bootstrap logto logto-proxy
```

- **首次全新装**：浏览器经 SSH 隧道开 `http://localhost:3002`（`ssh -L 3002:localhost:3002 <ECS>`）→ setup admin → 建 SPA + M2M 应用 → 拷 `LOGTO_*` 回填 `.env.prod`。**还需 SQL 补两项**（否则登录失败）：API resource（indicator = `https://gw.ops.spider-net.com.cn` = `OIDC_AUDIENCE`）、SPA 的 `alwaysIssueRefreshToken`（具体 SQL 向 Optima 索取）。
- **重装（Logto 库在 RDS 未丢）**：无需 setup，`.env.prod` 里 `LOGTO_*` 沿用原值，直接起即可。

**验证**：`docker logs sibada-logto` healthy；`curl -s localhost:3001/oidc/.well-known/openid-configuration | head` 有 issuer。

### 阶段 D — 起全部服务

```bash
cd /opt/sibada/docker
# 1) minio 先就绪，再建 bucket。minio-init 依赖 minio: service_healthy —— 别用 --no-deps，
#    否则它不等 minio 起好、mc mb 失败仍 exit 0，bucket optima-skills 可能没建成。
docker compose -f compose.prod.yml --env-file .env.prod up -d minio
docker compose -f compose.prod.yml --env-file .env.prod up minio-init   # 等 healthy → 建 bucket → 退出
# 2) 其余常驻服务 + 网关（--no-deps：避免 caddy/backend 的 depends 把 migrate 门禁拖进来）
docker compose -f compose.prod.yml --env-file .env.prod up -d --no-deps \
  caddy optima-skills redis optima-generation scout-backend agent-runtime gw-core gw-admin
# 3) 迁移
#   - 数据恢复（库已在）：跳过本步
#   - 全新空库：跑一次 sibada-migrate（seed 步骤恒 exit 1，已知无害）
docker compose -f compose.prod.yml --env-file .env.prod up sibada-migrate || true
#   - 仅全新空库还需手动建 optima-generation 的表（现行镜像 entrypoint 不跑 migration，
#     否则图片/数字人生成报 relation "tasks" does not exist）。幂等：
docker exec -w /app/packages/generation sibada-generation node dist/db/migrate.js
# 4) 业务后端 + 前端
#   backend depends_on sibada-migrate（service_completed_successfully），而 migrate 的 seed 恒
#   exit 1 → 用 --no-deps 绕开这个门禁（web 只经 backend 传递依赖 migrate，同批带上）。
docker compose -f compose.prod.yml --env-file .env.prod up -d --no-deps sibada-backend sibada-web
```

- **坑**：`LOCAL_AGENT_NETWORK=sibada-prod_default`（= 项目名 `sibada-prod` + `_default`）。项目名变了 bridge 必 spawn 失败。
- **坑**：换过 `sibada-agent:prod` 镜像后，`docker rm -f` 掉旧 `optima-bridge-ses_*`，下条消息才用新镜像起 bridge。

**验证**：`docker compose -f compose.prod.yml ps` **13 个常驻容器全 `Up`**；run-once（`logto-bootstrap` / `minio-init` / `sibada-migrate`）Exited，其中 `sibada-migrate` exit 1 属正常；`logto-password-applier` 仅在用「自动应用 admin 密码」方式（非浏览器 setup 向导）时才启动。Caddy 日志 6 站点块 / 7 域名（含 `console.`）证书签发成功。

### 5.1 三层备份现状（2026-07-25）

### 5.2 RDS 恢复

RDS 开着 7 天自动备份（全量 + 日志，可按时间点恢复）。恢复走**阿里云 RDS 控制台**：

- **克隆到新实例**（推荐，不覆盖现有）：按备份集/时间点「克隆实例」→ 拿到新实例内网地址 → 改 `.env.prod` 的 `RDS_HOST` → `up -d --no-deps --force-recreate` 所有连库的服务。
- **恢复到原实例**：按时间点回滚（会覆盖，慎用）。
- 🔴 **必须配回原 `.env.prod`（同 `ENCRYPTION_KEY`/`JWT_SECRET`）**，否则加密字段/会话失效。
- 🟡 **建议本院阿里云运维**：把保留期从 7 天适当延长 + 开启 PITR 保护。

### 5.3 NAS 恢复

⚠️ **当前 NAS 没有任何快照/备份策略。** 一旦 NAS 数据丢失：

| NAS 内容 | 丢失影响 | 可否重建 |
|----------|----------|----------|
| `_shared/kb`（企业知识库 bare repo `sibada-kb.git`） | AI 引用不到医学知识库 | 部分——可从上游再同步，但本院知识库已分叉（显示名 / 目录名做过定制），同步时勿覆盖这些定制 |
| `{userId}`（每个用户的会话工作空间文件） | 用户历史生成的文件丢失 | ❌ 不可重建 |
| `_published`（成片视频） | 已发布视频文件丢失 | ❌ 不可重建 |

> 🔴 **行动项（归本院阿里云运维）**：给这个通用型标准 NAS **配置自动快照策略**（阿里云 NAS 支持快照，频率/保留期按需）。这是当前 DR 的最大缺口，建议尽快补上。
>
> **恢复流程（有快照后）**：阿里云 NAS 控制台按快照「回滚文件系统」，或「用快照创建新文件系统」→ 若换了挂载点，改 ECS `/etc/fstab` 与重挂 `/mnt/nas/sibada`。

## 7. 当前基线 + 真实踩过的坑速查

### 7.1 镜像基线（下次 diff / 回滚用）

**查当前基线**：`docker compose -f /opt/sibada/docker/compose.prod.yml images`。

**回滚惯例**：每次升级前，Optima 都会把当时现役镜像另打一个 `:prod-pre-<日期>`（或 `:prod-pre-<特性>`）备份 tag。回滚 = 把该 tag 重新指回 `:prod` + recreate 对应服务（见上面「回滚」小节）。查本机有哪些备份 tag：`docker images | grep prod-pre`。

### 7.2 坑速查（重建/运维时高频）

| 坑 | 症状 | 处理 |
|----|------|------|
| ACR VPC endpoint DNS 丢 | push/pull `no such host` | `/etc/hosts` pin `<ACR endpoint 内网 IP> <ACR-VPC-endpoint>`；根治=控制台开自动 DNS |
| 根盘满 | 会话刷新变空、gw-core 日志断档 | docker/containerd 数据放 `/mnt/data`（[§4 A.1](#阶段-a--ecs-初始化)）；`df -h /` 告警 |
| `SILICONFLOW_BASE_URL` 用了 `.com` | AI 回复 401 | 改 `.cn`（国内站 key） |
| `HEYGEN_BASE_URL` 留空/直连 | 数字人训练返回空错误 | 走反代 `<HeyGen 反代地址（向 Optima 索取）>` |
| HeyGen「没积分」 | 网页有套餐分但 API 报没积分 | HeyGen 是**双钱包**，需单独买 **API credits**（别换 key，会丢数字人/音色） |
| GrsAI「额度不足」 | 账户有积分、key 没错仍报 | 该 key 被单独设了**消费限额**（与账户积分无关），到 GrsAI 后台解除 |
| `sibada-migrate` seed | run-once 容器 exit 1 | **已知无害**（migration 已应用，seed 是假数据）；起服务用 `--no-deps` |
| `LOCAL_AGENT_NETWORK` 不对 | bridge spawn 全失败 | 必须 `sibada-prod_default`（= compose 项目名 + `_default`） |
| 换 `sibada-agent:prod` 后旧 bridge 还在 | 新技能不生效 | `docker rm -f optima-bridge-*`（用户抢先重连需再 rm 一次） |
| `SIBADA_LOGTO_CLIENT_ID` 兜底残留 | 区域管理入口不出现 | 配 `SIBADA_WEB_LOGTO_APP_ID`（backend 由它派生 admin 闸口） |
| Logto 手工建 app 不够 | callback `invalid_target` / 无 refresh token | SQL 补 API resource（`OIDC_AUDIENCE`）+ `alwaysIssueRefreshToken`（bringup-notes） |
| 手工 migration 表 owner 错 | backend 42501 / 页面 500 | `ALTER TABLE ... OWNER TO sibada_dev` |
| DASHSCOPE 没透传给 bridge | OCR/语音空转 | gw-core `PASSTHROUGH_ENV_KEYS` 含 `DASHSCOPE_API_KEY`，改后 recreate gw-core |
| build 脚本 `set -e` + `&&` 陷阱 | build 失败却打「成功」、镜像没更新 | 每步显式 `; echo EXIT=$?` 判，别用 AND-OR 串 |
| 第三方账户「没钱」 | 某功能首次真用才爆（HeyGen/SiliconFlow/GrsAI/DashScope/TikHub） | 用付费端点探针验 key；建议各账户配余额告警 |

> 更完整的首次 bring-up 细节与持续更新的运维实况由 Optima 保管，需要时联系我们。
